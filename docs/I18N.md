# Language packs

PairPocket keeps every user-visible string in JSON language packs. Korean (`ko`) is the source of truth: a string is written in Korean first, and every other language is a translation of the same key. A new language works as soon as its pack is translated; no component code changes.

## Where text lives

| What | Where | Notes |
| --- | --- | --- |
| Web UI text | `frontend/messages/<code>.json` | next-intl ICU messages (`{name}`, `{count, plural, ...}`) |
| Emails sent by the API | `backend/app/locales/<code>.json` | Python `str.format` placeholders (`{name}`) |
| API error text | `frontend/messages/<code>.json` under `errors.server.*` | The API sends a code, the UI translates it |
| Language list | `frontend/i18n/locales.json` | Mirrored in `backend/app/core/locales.json` |

Some Korean strings in code are data, not text, and must not be translated:

- Category and sub-category values (`frontend/lib/category-values.ts`, `backend/app/models/category_preset.py`). They are stored in MongoDB and used in AI prompts. The UI shows them through `categories.*` and `subCategories.*` in the packs.
- Korean institution ids in `frontend/lib/banks.ts` (stored on accounts). Their display names come from `banks.*`.
- The merchant placeholder `미지정` and the line item unit `개`, which the API stores. The UI shows `common.unspecified` and `transaction.unitPiece`.

## How a page gets its text

`frontend/i18n/messages.ts` merges packs for the requested locale, least specific first:

1. `ko.json` (complete, the source)
2. `en.json` (complete, the fallback for other languages)
3. `<code>.json` for the requested language, if it exists

Missing keys and empty strings in a pack are skipped, so they show the English text. A language listed in `locales.json` without any pack shows English everywhere until its pack lands.

Dates and numbers use the `intl` tag of the locale (`intlLocale()` in `frontend/i18n/locales.ts`). Never hardcode `"ko-KR"` or `"en-CA"` for display formatting.

## API errors

The API never sends display text for errors. Every user-facing error is an `AppError` (`backend/app/core/errors.py`) with a camelCase code and optional params:

```json
{ "detail": "accountNotFound", "code": "accountNotFound", "params": { "field": "fromAccount" } }
```

The UI turns it into `errors.server.accountNotFound`, translating the `field` param through `errors.fields.*` and a `ledger` param through `errors.ledgers.*` (`frontend/lib/errors.ts`). Components show errors with `translateError` or `errorMessage`, never `err.message`.

```python
raise AppError(status.HTTP_422_UNPROCESSABLE_ENTITY, "selectedAccountNotFound", field="fromAccount")
```

AI scan streams report failures the same way, as `{ "event": "error", "code": "geminiKeyMissing", "params": {} }`; the `error` field next to it is a diagnostic for logs and is never shown.

When you add an error code in the backend, add `errors.server.<code>` to `ko.json` and `en.json`. `backend/tests/test_i18n_packs.py` fails if a code used in the backend is missing from the packs, if a message uses a placeholder the API does not send, if an `errors.server` key is no longer used, or if a route raises `HTTPException` with text.

## Emails

Emails are written in the recipient's first preferred language (Korean when none is saved); an invitation uses the inviter's language because the invitee may not have an account yet. Links in emails carry the same locale prefix (`/ko/...`). Use `translate(locale, "email.<key>", **params)` from `backend/app/core/i18n.py`.

## Adding or changing text

1. Add the key to `frontend/messages/ko.json` and the English text to `en.json` (same key, same placeholders).
2. Use it with `useTranslations("<namespace>")` (client) or `getTranslations` (server).
3. Run `npm run check:i18n` in `frontend`.

Never write Korean or English UI text directly in components. The check fails on any Korean in `app/`, `components/`, `lib/` or `i18n/` outside the data modules listed above.

## Adding a language

```bash
cd frontend
npm run i18n:new -- ja --native "日本語" --label "日本語" --intl ja-JP --short JA
```

This registers `ja` in both registries (as beta) and creates `frontend/messages/ja.json` and `backend/app/locales/ja.json` with every key present and empty values. Then:

1. Translate the values. `npm run i18n:missing -- ja` lists every untranslated key with the Korean source and the English reference. Translating from a copy of `ko.json` or `en.json` also works: any subset of keys is valid.
2. Keep placeholders exactly as in Korean: `{count}` stays `{count}`. Plural and select blocks may change shape (`{count, plural, one {...} other {...}}`) but must keep the same argument names.
3. Run `npm run check:i18n`. It fails on unknown keys, placeholder mismatches and broken ICU syntax, and warns about untranslated keys.
4. `npm run i18n:status` shows coverage for every language. When a pack reaches 100%, set `"beta": false` for it in `frontend/i18n/locales.json` and `backend/app/core/locales.json` to drop the Beta badge.

The locale code must be a BCP 47 tag (`fr`, `zh-Hant`, `pt-BR`). For a regional variant you can list a parent pack to try before English with `"fallback": ["pt"]` in its registry entry.

## Checks

| Command | Purpose |
| --- | --- |
| `npm run check:i18n` | CI gate: registry sync, key and placeholder parity, ICU syntax, hardcoded Korean |
| `npm run i18n:status` | Coverage per language and pack |
| `npm run i18n:missing -- <code>` | Untranslated keys with source text |
| `npm run i18n:new -- <code>` | Register a language and scaffold its packs |
| `pytest tests/test_i18n_packs.py` (backend) | Backend pack parity and API error codes present in the UI packs |
